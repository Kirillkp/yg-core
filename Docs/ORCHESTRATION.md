# Оркестрация агентов (ЧЕРНОВИК, ждёт утверждения владельца)

Как агенты делают игры на `yg-core`: кто за что отвечает, какая модель берётся под какую сложность, где обязателен человек. Документ общий для всех агентов (Claude Code, Codex и других). Источник правды лежит в `yg-core`, шаблоны и игры получают закреплённую копию (раздел «Распространение»).

## Принципы

1. **Один основной файл для всех агентов:** `AGENTS.md`. `CLAUDE.md` состоит из одной строки-ссылки на него. Всё, что нужно только одному инструменту (субагенты, навыки), лежит отдельно и необязательно.
2. **Компактный контекст.** Агент читает `Docs/AGENT_CONTEXT.md`, затем файл своей задачи, затем только относящиеся к задаче спецификации. Весь `Docs/` по умолчанию не читается.
3. **Реализует один агент на задачу**, в своей ветке или worktree. Параллельно запускаются только независимые задачи на чтение (анализ, ревью, поиск регрессий).
4. **Человек подтверждает** то, что перечислено в разделе «Точки утверждения». Остальное агенты делают сами.
5. Общие правила проекта: комментарии в коде на русском; документ версии обязателен; Unity, сборки и долгие проверки без явного запроса не запускаются; `Library`, `Temp`, `Builds`, `Logs`, `UserSettings` не коммитятся; push, тег и всё необратимое только после вопроса.

## Роли

| Роль | Что делает | Уровень по умолчанию |
|---|---|---|
| Оркестратор | Принимает запрос владельца, разбивает на задачи, **предлагает уровень, модель и Effort каждой**, ведёт очередь, готовит промты для референсов, собирает результаты. Сам код пишет только в мелочах | L2 |
| Архитектор | Проектирует модуль или фичу, пишет решение в `Docs/DECISIONS.md` и ТЗ для исполнителя | L2 (`high`) |
| **Исполнитель** | Общая роль: реализует задачу по ТЗ до конца, **включая сборку, компиляцию и свои проверки**. Специализации ниже | L2 (L1 для механики; L3 только для 3D в Blender) |
| Ревьюер | Один раз независимо читает diff и проверяет платформенное поведение (стенд, консоль Яндекса). Код не правит, возвращает замечания исполнителю | L2 (`high` для рискованного) |

Специализации исполнителя:

| Специализация | Область | Особенность приёмки |
|---|---|---|
| Разработчик | Unity, C#, сцены, префабы, UI, пакет `yg-core` | Ворота качества ниже |
| 3D-художник (Blender) | Модели, риги, анимации, экспорт в Unity, скрипты Blender | Результат показывается владельцу на превью и утверждается им до импорта в проект |

Дизайн-референсы это не отдельный агент, а процесс (раздел «Дизайн-референсы через Codex»). Роли это функции: небольшую задачу один агент может пройти по ролям последовательно.

## Уровни сложности и модели

| Уровень | Когда | Примеры |
|---|---|---|
| **L3** (тяжёлый) | **Только 3D-моделирование в Blender**: модели, риги, анимации | Персонаж, окружение, анимации бега и прыжка, экспорт в Unity |
| **L2** (средний, по умолчанию) | Всё остальное, включая рискованное | Фичи, экраны, игровой цикл, пакет, стенд, архитектура, **сохранения, покупки, авторизация, платформенные заплатки**, ревью |
| **L1** (лёгкий) | Механическая работа без рисков | Документы, переименования, перенос по образцу, тексты и локализация |

**Страховка для рискованного на L2.** Сохранения, покупки, авторизация и платформенный код выполняет L2, но с Effort `high`, обязательным проходом ревьюера и прогоном на стенде или в черновике консоли. Если исполнитель дважды не справился, он останавливается и возвращает задачу оркестратору, а не продолжает наугад.

### Модели и Effort (Claude)

| Уровень | Модель | Effort по умолчанию | Когда повышать |
|---|---|---|---|
| L3 (Blender) | Opus 5.5 (`claude-opus-5-5`) | `high` | `xhigh` для рига и сложных анимаций |
| L2 | Sonnet 5.5 (`claude-sonnet-5-5`) | `medium` | `high` для рискованного (см. выше), архитектуры и сложной отладки |
| L1 | Haiku 5.5 (`claude-haiku-5-5`) | `low` | `medium`, если лёгкая модель дважды не справилась |
| Оркестратор | Sonnet 5.5 | `medium` | `high` для неоднозначного запроса и разбиения большой работы |

Допустимые значения Effort: `low`, `medium`, `high`, `xhigh`, `max`. `max` только по решению владельца.

### Модели и Effort (Codex)

Источник: официальная страница моделей Codex (на 2026-10-11). Названия и идентификаторы там меняются, поэтому актуальная таблица ведётся в `Agents/models.md`, а перед использованием идентификатор сверяется командой `/model`.

| Уровень | Модель (идентификатор) | Effort по умолчанию | Когда повышать |
|---|---|---|---|
| L3 (Blender) | GPT-6 Astra (`gpt-6-astra`) | `high` | `xhigh` для рига и сложных анимаций |
| L2 | GPT-6.1 Sol (`gpt-6.1-sol`) | `medium` | `high` для рискованного, архитектуры и сложной отладки |
| L1 | GPT-6 Luna (`gpt-6-luna`) | `low` | `medium`, если лёгкая модель дважды не справилась |

Шкала Effort в CLI: `low`, `medium`, `high`, `xhigh`, `max`, `ultra` (в приложении: Light, Medium, High, Extra High, Max, Ultra). Для GPT-6 Luna максимум `max`. Названия верхних уровней в CLI официальная страница не перечисляет, они взяты из каталога моделей и проверяются через `/model`. `max` и `ultra` только по решению владельца. GPT-5.5 не использовать: он снимается с Codex 2026-10-14.

Таблица живёт в `Agents/models.md` и меняется без правки процесса. В файле задачи Effort указывается всегда.

### Выбор уровня (первая итерация)

1. Оркестратор ставит в задаче **предложенные уровень, модель и Effort** и коротко пишет почему.
2. **Владелец подтверждает или меняет их до старта задачи.** Без утверждения задача не начинается.
3. После утверждения поле «утверждённый уровень» не меняется самим агентом. Если по ходу выясняется, что нужен другой уровень или выше Effort, исполнитель останавливается и возвращает задачу оркестратору с причиной (это снова идёт на подтверждение).
4. Когда накопится достаточно задач с совпавшими предложениями, подтверждение можно ослабить (например, только для L3). Это отдельное решение владельца.

## Точки утверждения человеком

Агент останавливается и спрашивает:

- **уровень, модель и Effort каждой задачи** (первая итерация, см. выше);
- **дизайн-референсы**: утверждаются владельцем в Codex до того, как исполнитель начнёт реализацию;
- **3D-результаты Blender** на превью, до импорта в проект;
- `git push`, создание тега, слияние в `main`, удаление веток;
- загрузка архива в консоль Яндекса, любые действия с покупками и деньгами (в том числе тестовыми в новой игре);
- приёмка геймплея и звука на слух (агент геймплей вручную не проверяет);
- удаление и перезапись данных, которые нельзя восстановить;
- изменение самих правил оркестрации.

## Файл задачи

Папка `Tasks/`, один файл на задачу, имя `TASK-NNN_кратко.md`.

```
# TASK-NNN: название
Статус: черновик | утверждена | в работе | на ревью | готова
Специализация: Разработчик | 3D-художник (Blender)
Уровень/модель/Effort (предложены): L2 / Sonnet 5.5 / medium — причина в одну строку
Уровень/модель/Effort (утверждены владельцем): — заполняет владелец
Референсы: пути к утверждённым файлам или «нужны» (тогда сначала этап референсов)
Контекст: какие спецификации и файлы читать (только нужные)
Что сделать: по пунктам
Не делать: границы
Критерии готовности: проверяемые
Ворота качества: какие из списка ниже обязательны
Результат: что изменилось, ссылки на файлы, что осталось непроверенным
```

## Ворота качества

Задача готова, когда пройдены все ворота, отмеченные в ней. Что не проверено, записывается в «Результат», а не умалчивается.

**Исполнитель проходит сам, до сдачи:**
1. Компиляция без ошибок (через Unity MCP), весь цикл «правка → компиляция → исправление» внутри одного агента.
2. `Tools/CoreChecks`, `Tools/YandexChecks`, `Tools/check-release.sh` для изменений пакета.
3. Документы обновлены: модульный документ, CHANGELOG, документ версии (для пакета и шаблонов).

**Ревьюер (один проход, только где нужно):**
4. Независимое чтение diff для всего, что трогает сохранения, покупки, авторизацию, платформенный код, и для L3.
5. Прогон на стенде или в черновике консоли Яндекса для платформенных изменений.
Замечания возвращаются исполнителю одним списком, а не по одной ошибке.

**Владелец:**
6. Приёмка там, где это в списке «Точки утверждения».

## Дизайн-референсы через Codex

Референсы генерирует Codex вместе с владельцем. Оркестратор (или Codex) только готовит задание, а согласование и сохранение идёт в чате Codex с владельцем.

1. Оркестратор пишет файл `Tasks/TASK-NNN/reference_prompt.md`, готовый к вставке в Codex. В нём:
   - **Контекст игры:** жанр, аудитория, платформа (Яндекс Игры, WebGL, телефон и ПК), стиль, палитра, уже утверждённые референсы;
   - **Что посмотреть:** точные пути к файлам проекта и ссылки (скриншоты, существующие экраны, спецификации);
   - **Что сгенерировать:** список экранов или ракурсов, размеры и ориентации, безопасные зоны интерфейса, какие состояния показать;
   - **Ограничения:** читаемость на маленьком экране, допустимые шрифты и размеры элементов, чего избегать;
   - **Куда сохранить:** папка и имена файлов из задачи;
   - **Правило:** показать варианты владельцу, вносить правки, **сохранять файлы только после явного согласия владельца**, после сохранения ответить «готово» и перечислить сохранённые файлы.
2. Владелец вставляет содержимое файла в Codex, обсуждает варианты и даёт согласие.
3. Codex сохраняет файлы по указанным путям и пишет «готово».
4. Оркестратор помечает референсы в задаче как утверждённые (пути, дата) и только после этого разрешает исполнителю начинать реализацию.

Без утверждённых референсов задача на экран или внешний вид не стартует.

## Контекст и экономия

Обязательное правило: сначала `Docs/AGENT_CONTEXT.md`, затем задача, затем точечные спецификации. Агент, который открыл весь `Docs/` без причины, нарушил правило. Отдельных лимитов бюджета нет (решение владельца).

## Распространение

- Источник: `yg-core/Agents/` (роли, `models.md`, шаблоны задач, `AGENTS.md`-основа).
- Шаблоны (`yg-template-empty`, `yg-template-roblox`) и игры получают закреплённую копию скриптом синхронизации с указанием тега `yg-core`.
- Править копию внутри шаблона или игры нельзя: правка идёт в `yg-core`, затем новый тег и синхронизация.
- Игровая часть (`AGENT_CONTEXT.md`, спецификации, задачи, решения) принадлежит игре и не синхронизируется.
