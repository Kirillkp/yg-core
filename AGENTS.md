# yg-core: инструкции для агентов

Это репозиторий общего Unity-пакета `com.kirillpolosov.yg-core` для игр на Яндекс Играх (WebGL) и тестового стенда `Stand/`, который проверяет пакет прямо на платформе.

Пакет выделен из игры «Обби Потоп» (`/Users/kirillpolosov/obby`). Код игры в пакет не входит.

## Порядок чтения

1. Этот файл.
2. `Packages/com.kirillpolosov.yg-core/Documentation~/00-index.md`: карта документации, «нужно X, читай Y».
3. Только тот модульный документ из `Documentation~/modules/`, который относится к задаче.
4. `Docs/CONVENTIONS.md`, если пишете или правите код.
5. `Docs/RELEASE_PROCESS.md`, если готовите версию.

Не читайте всё подряд. Индекс сам указывает, что нужно.

## Что где лежит

| Путь | Что это |
|---|---|
| `Packages/com.kirillpolosov.yg-core/` | Сам пакет: код, документация, журнал версий |
| `Packages/com.kirillpolosov.yg-core/Documentation~/` | Документация пакета (в сборку игры не попадает) |
| `Stand/` | Unity-проект тестового стенда, подключает пакет локально |
| `Docs/` | Процесс: выпуск версий, чек-лист стенда, решения, план переноса из «Обби» |
| `Tools/` | `check-release.sh` (проверка выпуска), `generate-meta.py` (файлы .meta), `CoreChecks/` (проверки логики без Unity) |

## Обязательные правила

1. **Комментарии в коде только на русском.** Заказчик читает код и должен понимать, что и зачем сделано. Имена классов, методов и переменных остаются английскими. Подробнее в `Docs/CONVENTIONS.md`.
2. **Документация часть работы.** Функция не готова, пока нет записи в модульном документе, кнопки с проверкой на стенде и строки в `CHANGELOG.md`.
3. **Игра не знает про Яндекс.** Прямые обращения к PluginYG2 и Яндекс SDK допустимы только в сборке `YgCore.Yandex`. Всё остальное работает через контракты (`YgCore.Contracts`).
4. **`YgCore.Core` и `YgCore.Contracts` ни от чего не зависят.** Не добавляйте им ссылок на другие сборки пакета.
5. **UI в пакет не входит.** Экраны живут в игре и в шаблонах. В пакете только логика.
6. **Формат сохранения меняется только вместе с версией схемы и миграцией.** Иначе обновление испортит прогресс игроков.
7. **Версионирование по SemVer.** `PATCH` исправление, `MINOR` новая возможность без поломок, `MAJOR` ломающее изменение (обязательна инструкция по переносу для игр).
8. **Тег версии ставится только после чек-листа стенда на Яндексе** и успешного `Tools/check-release.sh`.
9. **Не запускайте Unity, сборки и тесты без явной просьбы пользователя.**
10. **Новые файлы в пакете получают `.meta`**: после добавления файлов выполните `python3 Tools/generate-meta.py`, иначе Unity проигнорирует пакет, подключённый из git. Логику, которую можно проверить без Unity, проверяйте в `Tools/CoreChecks` (`dotnet run --project Tools/CoreChecks`).
11. **Не коммитьте** `Library`, `Temp`, `Build`, `Builds`, `Logs`, `UserSettings` и другие сгенерированные папки Unity.
12. **Решения фиксируются** в `Docs/DECISIONS.md`. Не пересматривайте принятое без явной просьбы.

## Определение «готово» для изменения в пакете

- [ ] Код с русскими комментариями.
- [ ] Обновлён модульный документ (`Documentation~/modules/…`).
- [ ] Добавлена или обновлена проверка на стенде.
- [ ] Запись в `CHANGELOG.md` под `[Unreleased]`.
- [ ] Если менялся формат сохранения: версия схемы и миграция, запись в `compatibility.md`.
- [ ] Если ломающее изменение: инструкция по переносу в `versions/`.

## Если вы оркестратор

- Раздавайте задачи исполнителям файлом задачи, а не пересказом: исполнитель читает только указанные документы.
- Лёгкие задачи (документы, переименования, поиск) отдавайте младшим моделям, SDK, сохранения и экономику старшим.
- Подключение пакета в новую игру: `Documentation~/install.md`.
- Обновление версии пакета в игре: `Documentation~/install.md`, раздел «Обновление».
- Живые игры закреплены на проверенной версии и обновляются только по решению пользователя.
